# Vibecodium React Native Operator Console: constraints and architecture decision note

## 1. Scope, date, and target platforms

**Date:** 2026-08-27
**Status:** source-backed architecture research; this note does not implement the console.

Vibecodium is a single-operator, self-hosted control plane with a React Native, mobile-first Operator Console. The host runs workflows independently of the mobile process and owns durable ordered events/segments, cursor replay, snapshots/catch-up, retention-gap responses, and push hints. **WorkflowControl** (start/stop/retry/configure/approve) and **SessionConsole** (live observation and direct typed input under an operator lease) are separate but linked planes. Workflows are immutable typed state machines described by JSON Schema. An `ExecutionRun` stream is normalized, per-stream ordered, at-least-once and cursor-replayable; terminal output is ordered segments, while live deltas may be coalesced. Provider-native stdout, ANSI, and PTY state are diagnostic escape hatches, not the product contract.

The target is one shared RN product on current supported iOS and Android releases, including small phones, large-font configurations, foreground/background transitions, intermittent connectivity, and low-end Android hardware. “Current” implementation details below are explicitly **current-main/RN-version-sensitive** where noted; they must be rechecked when the supported RN version changes.

## 3. Recommended semantic console architecture

### 3.1 Two linked planes and one authoritative host

The host is the authority for both planes. **WorkflowControl** operates immutable, typed state machines: the client submits validated commands such as start, stop, retry, approve, or configure, and renders acknowledged state transitions. **SessionConsole** observes an `ExecutionRun` and, when granted an operator lease, submits typed command-queue entries. A lease has an owner, expiry/renewal, and an explicit “not granted/expired” state; direct input is never an unstructured socket write. Both planes link to the same run/stream IDs, but neither makes the other a hidden terminal emulator.

The host normalizes provider output into an at-least-once event stream. Each event should carry a stable event ID, stream ID, monotonic per-stream sequence/cursor, schema version, event kind, and payload. The host persists ordered terminal segments and may coalesce live deltas before delivery. The semantic event types are the UI contract: status, milestone, tool/action, output chunk/segment, error, control/approval, input acknowledgement, artifact reference, and terminal state. JSON Schema validates workflow commands, event envelopes, and typed payloads at the boundary.

### 3.2 Event-to-view model

The RN client folds events into a derived view model rather than rendering transport frames directly:

- run header: workflow, run state, connectivity, lease state, latest cursor, and retention warning;
- semantic timeline: stable rows for status/milestone/tool/control/result/error events;
- output chunks: ordered, append-only segments with transient deltas coalesced into bounded updates;
- action model: typed controls (retry, cancel, approve, copy, expand, retry catch-up) enabled by server state and lease;
- diagnostic attachment: raw-log availability, byte range/segment references, and download/copy affordances.

Store the canonical client model outside individual row components. Rows are memoized and keyed by stable event/segment IDs; a row never owns the only copy of history. The visible/cache model has explicit bounds (for example, a recent window plus an older-page affordance), while a cursor and host query provide the authoritative route to anything evicted locally. This prevents `FlatList` virtualization from turning off-window component state into lost run history.

### 3.3 Rows, chunks, and output volume

Use `FlatList`/`VirtualizedList` for semantic rows, not `ScrollView` for unbounded output. Choose a row/chunk size that keeps text selectable and accessible; do not split by UTF-16 code unit. For output that is visually code-like, preserve line breaks and style spans in semantic chunks, but treat grapheme segmentation and display columns as separate policies. A fixed-cell view is a later specialized visualization, not the initial console model.

The host applies per-stream rate and batch limits. The RN client applies a bounded queue and coalesces only transient live deltas. It must not discard acknowledged/persisted events merely because animation or rendering is behind. If the live queue exceeds its cap, stop trying to animate faster: reduce delta frequency, request a catch-up/snapshot, or surface an overload state. Every persisted event remains recoverable by cursor or snapshot. Dedupe at event ID and `(stream, sequence)` makes reconnect and at-least-once delivery safe.

### 3.4 Animation boundaries and reduced motion

Animation is explanatory chrome, not a second event stream. Animate connection changes, state transitions, a bounded activity indicator, lease status, and a cursor/focus affordance. Do not animate every glyph, historical row, or token. Reanimated is acceptable for these bounded non-layout properties if already available, but performance must be profiled in release builds. RN `Animated` has no automatic reduced-motion policy ([caveats](https://reactnative.dev/docs/animations#caveats)); Reanimated offers `useReducedMotion`, `ReducedMotionConfig`, and per-animation `reduceMotion` ([device setting](https://docs.swmansion.com/react-native-reanimated/docs/device/useReducedMotion/), [config](https://docs.swmansion.com/react-native-reanimated/docs/device/ReducedMotionConfig/), [timing](https://docs.swmansion.com/react-native-reanimated/docs/animations/withTiming/)). Because `useReducedMotion` only reflects the setting at app start and does not itself rerender on setting changes, subscribe to `AccessibilityInfo` changes and update the console’s animation policy explicitly. On reduced motion, replace movement with immediate state changes, dissolve, or a non-moving highlight.

### 3.5 Raw-log escape hatch

The host may retain raw provider bytes/chunks, ANSI/ECMA-48 input, PTY metadata, and parser diagnostics alongside semantic events. The RN console exposes this as a clearly labeled raw-log view with copy/download, search where feasible, and an explanation that fidelity is diagnostic and provider-specific. Raw bytes are not reinterpreted as the canonical semantic timeline. Binary WebSocket frames may carry bytes when needed; semantic JSON remains primary. A full VT emulator is deferred until a real provider requirement, fidelity test, selection model, and accessibility plan justify it.

### 3.6 Cursor catch-up and retention gaps

On foreground entry or reconnect, the client sends its persisted last cursor and requests an authenticated HTTP snapshot/catch-up. The host responds with either a snapshot plus ordered events after the cursor, or an explicit retention gap with the latest valid snapshot/cursor. The client applies snapshot, then events, deduplicating overlaps; it never assumes that a socket was continuously alive. A gap is visible in the timeline (“older history is no longer retained”), with the recovered snapshot and a clear boundary, rather than silently presenting a truncated run. The client stores the new cursor only after the corresponding event/snapshot is accepted.

The normal foreground sequence is: observe AppState/focus, debounce reconnect, open live WebSocket, request catch-up, apply/dedupe, then render bounded live batches. Background sockets are quiesced; notifications may wake the user, but the next authoritative operation is still catch-up. Host retention policy and gap semantics are part of the protocol, not a client guess.

### 3.7 Provider-agnostic boundary

Adapters negotiate capabilities such as streaming, cancellation, approval, artifact references, PTY diagnostics, or structured tool events. The common schema promises only normalized IDs/order, semantic event kinds, run/session/workflow status, typed result/error/control/input, replay/cursor behavior, and accessibility meaning. ANSI bytes, PTY resize/cursor state, raw frames, provider reasoning, approval details, cost metadata, and native handles remain optional provider fields. A provider that lacks a capability renders a truthful unavailable state; the console must never fabricate equivalent behavior.

## 5. Library choices and non-choices

1. **Baseline: existing RN primitives.** Use `FlatList`/`VirtualizedList`, `View`, native `Text`, `Pressable`/buttons, `AccessibilityInfo`, `AppState`, HTTP, and WebSocket already provided by the application stack. This minimizes native surface area and preserves semantic accessibility. `ScrollView` remains appropriate for small bounded control forms, not an unbounded run log.
2. **Animation: optional existing Reanimated.** Reanimated is a good fit for bounded status/cursor chrome when the app already carries it, but its worklets do not solve event transport or history, and its reduced-motion hook requires an explicit setting-change subscription. Do not add animation to the event path just to make streaming look busy.
3. **FlashList: profile-gated option, not a dependency decision.** [FlashList](https://shopify.github.io/flash-list/docs/) recycles cells and is New Architecture-oriented; recycling requires careful reset of internal state and keys ([recycling](https://shopify.github.io/flash-list/docs/recycling)). Consider it only if release profiling demonstrates that the semantic `FlatList` model is insufficient. A swap is not free: test row state, focus, large fonts, and accessibility again.
4. **Skia: specialized visualization only.** [Skia Canvas](https://shopify.github.io/react-native-skia/docs/canvas/overview/) and [Paragraph](https://shopify.github.io/react-native-skia/docs/text/paragraph/) can support a dense fixed-cell visualization with custom/system fonts. Canvas needs overlay RN views or a virtual accessibility tree, and variable draw-command counts require profiling. It is not the semantic baseline and should not be introduced for ordinary timeline rows.
5. **Terminal emulators: deliberately deferred.** [xterm.js](https://github.com/xtermjs/xterm.js/blob/master/README.md) is browser/DOM-oriented; [SwiftTerm](https://github.com/migueldeicaza/SwiftTerm/blob/main/README.md) is an iOS/UIKit-oriented option and does not imply local iOS processes. Do not add either, or a native ANSI/PTY emulator, until an actual VT-fidelity requirement survives the semantic prototype and includes selection, copy, security/redaction, lifecycle, and accessibility acceptance criteria.
6. **SSE: non-choice for the baseline.** `Last-Event-ID` is useful replay-adjacent metadata, but SSE has no receive backpressure and RN has no official EventSource baseline. It is not a shortcut around the host cursor/snapshot protocol.
7. **No dependency additions in this research phase.** The architecture should be validated with the existing RN stack first. Reanimated, FlashList, Skia, a terminal engine, or an EventSource/native networking module are optional, separately justified decisions—not implicit requirements.

## 6. Open questions for the two-plane prototype and final ratification

1. What exact JSON Schema envelope and versioning rules are required for workflow commands, lease/typed-input commands, event IDs, stream sequences, cursors, artifacts, errors, and capability negotiation? Which fields are immutable after persistence?
2. What host batch/rate limits, client queue/window limits, and delta-coalescing interval preserve responsiveness on the slowest target device? When overloaded, should the client request a snapshot, reduce live frequency, or show a paused-live indicator, and which data-loss invariant is non-negotiable?
3. What are the output segment boundaries and limits for very long lines, binary data, multiline tool output, and copy/download? Which raw bytes are retained, redacted, encrypted, or expired, and how is the semantic-to-raw relationship displayed?
4. What retention duration and cursor-expiry policy produce a useful gap UX? Define the snapshot-plus-gap response, wording, recovered-history boundary, and whether the operator can request older archived artifacts.
5. What are the WorkflowControl and SessionConsole authorization rules, lease renewal/expiry behavior, command queue ordering, cancellation semantics, and approval UX when a second tab/device or a stale client is present?
6. Which provider capabilities are mandatory for the first release, and which remain optional? Ratify the common schema and the truthful unavailable states before adding provider-specific fields; do not assume stdout/ANSI/PTY or reasoning parity.
7. What RN version, New Architecture mode, minimum iOS/Android versions, device classes, font scales (including large-text settings), and font bundle policy are supported? The prototype must measure fallback glyph coverage, grapheme behavior, row reflow, focus, and list performance on that matrix.
8. Which notification hints are actionable versus informational, what privacy/redaction constraints apply to them, and is there a real user-visible Android monitoring mode that justifies a foreground service? Otherwise keep APNs/FCM and all background tasks as best-effort wake/alert mechanisms.
9. What accessibility contract will be ratified for each semantic row and action: labels, roles, state/value, focus order, live-region policy, milestone announcements, non-color status, copy/retry/expand/raw-log actions, and reduced-motion replacements? Validate with VoiceOver/TalkBack and large-font reflow, not only snapshots.
10. What prototype evidence is sufficient for final ratification? At minimum, exercise high-volume deltas, duplicate/reordered delivery, disconnect/background/foreground, missing push hints, retention gaps, lease expiry, raw-log escape, reduced motion, screen-reader navigation, and large fonts; record frame responsiveness, memory, event completeness, and recovery time in release builds.
